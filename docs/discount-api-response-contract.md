# WooCommerce Discount API Response Contract

Source of truth: `pinaka-pos/v1/custom-discount` and `pinaka-pos/v1/assets/discount-rules` in the supplied `pinaka-pos-wp` ZIP. Empty-group keys are omitted by the WordPress list implementation; examples below show representative populated groups.

The PCH CRUD route is store-scoped. Its `:type` values are `auto`, `mix_match`, and `multipack`. PCH forwards the WordPress JSON body (including its wrappers, omitted keys, message text, and values) and its HTTP error status where the source returns a non-2xx response.

PCH stores the grouped snapshot in the existing `store_discounts` row per store and mirrors individual records to `public.discounts` for per-discount lookups. Startup creates the mirror table and unique key if they are absent, then backfills it from existing snapshots without truncating records. Create, update, and sync upsert mirror rows; successful delete marks the mirror row `is_deleted=true`. The all-types list accepts `?type=auto`, `?type=mix_match`, or `?type=multipack` to return that source group as `data[]`; typed list aliases remain available.

The same PCH handlers are also mounted under `/connector/api/v1/stores`; the table uses the `/api/v1/stores` alias.

## Other WordPress routes found

| Route | Response contract / relationship to these discount records |
|---|---|
| `GET /wp-json/pinaka-pos/v1/assets/discount-rules` → `GET /api/v1/stores/:storeId/discount-rules` | Separate top-level array of rule projections (`ruleId`, `ruleType`, product IDs, price/quantity fields, `active`). PCH forwards this array unchanged; it is distinct from the grouped admin list response. |
| `POST /wp-json/pinaka-pos/v1/custom-discount/by-ids` → `POST /api/v1/stores/:storeId/discounts/by-ids` | Product lookup used by discount management, not a discount record lookup. Returns `{"data":[]}` for empty input or `{"data":[{"id":8,"name":"Item"}]}`; PCH forwards either response unchanged. |
| `POST /wp-json/pinaka-pos/v1/custom-discount/apply/:order_id` → `POST /api/v1/stores/:storeId/discounts/apply/:orderId` | Order-level custom-code application. Success body is `{"success":true,"message":"Discount applied to order.","discount_code":"…","discount_amount":"…","order_id":123}`; validation failures use the source `{success:false,message}` body and source 400/404 status. PCH forwards body and status unchanged. |
| `POST /wp-json/pinaka-pos/v1/custom-discount/remove/:order_id` → `POST /api/v1/stores/:storeId/discounts/remove/:orderId` | Successful removal returns the dynamic WooCommerce order REST response from `prepare_object_for_response()->get_data()`; missing order / fee returns the source `{success:false,message}` object with 404. PCH forwards body and status unchanged. |

Multipack create’s WordPress response has no discount ID. PCH compares the existing and resulting list records, adds the resolved `id` to its create response, and stores the local mapping. If the list API cannot reveal a new ID, PCH returns the original create response and a later pull can rebuild the mapping. The supplied plugin source ZIP is left unchanged.
